8. Scoring model

The system should produce scores for:

1. Value potential
2. Feasibility
3. Urgency
4. Data readiness
5. Automation suitability
6. AI suitability
7. Overall project fit

Use simple, explainable scores from 1 to 5.

Core equation

\text{Project Fit} = \text{Value Potential} \times \text{Feasibility} \times \text{Urgency}

Spoken form:

Project fit equals value potential times feasibility times urgency.

Because it is multiplicative, a weak feasibility score reduces the overall recommendation even if the business value sounds high. That is good. It prevents fantasy-project inflation.

More detailed weighted version

S = w_vV + w_fF + w_uU + w_dD + w_rR - w_cC

Where:

* S = total score
* V = value potential
* F = feasibility
* U = urgency
* D = data readiness
* R = repeatability
* C = complexity/risk penalty
* w_i = weighting coefficients

Spoken form:

Total score equals weight v times value potential, plus weight f times feasibility, plus weight u times urgency, plus weight d times data readiness, plus weight r times repeatability, minus weight c times complexity.

Recommended initial weights:

Component	Weight
Value potential	0.25
Feasibility	0.25
Urgency	0.15
Data readiness	0.15
Repeatability	0.15
Complexity penalty	0.05

For MVP, the LLM can infer these qualitatively from text. Later, follow-up questions can calibrate them numerically.

4.3 Prompt principles

The system prompt should instruct the model to:

1. Classify conservatively.
2. Prefer simple solutions before advanced ML/AI.
3. Recommend AI only when language, documents, search, summarisation, or flexible reasoning is central.
4. Recommend forecasting only when time-indexed historical data is implied or likely.
5. Recommend customer intelligence only when customer/order/sales data is involved.
6. Recommend data readiness if the problem is vague or data access seems poor.
7. Avoid promising exact savings or guaranteed ROI.
8. Produce practical first steps.
9. Use plain English for user-facing outputs.
10. Use technical depth in the gated roadmap, but keep it SME-readable.

12. My recommendation on single prompt versus follow-up questions

Your instinct is right: aim for single prompt first.

That is lower friction and more elegant.

But include a fallback:

* If confidence is high or medium: produce instant classification.
* If confidence is low: still produce a tentative classification, but ask one follow-up question.

Example:

This may be a Reporting Automation problem, but I need one detail to be more useful:
Is the report created from the same data source each time, or does someone manually gather information from several places?

Do not turn it into a long chat unless necessary.

The product promise should be:

“Describe the problem once. Get a useful first map.”

Not:

“Answer twelve questions before anything happens.”
